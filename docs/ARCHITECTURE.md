# 墨境 · 技术架构

## 1. 定位

墨境的核心不是某一家大模型，而是一个小说垂直的持久执行系统。

系统把模型当作可替换的推理/写作能力；作品状态、任务深度、工具权限、长期记忆、结构硬门、质量兜底、事务提交、恢复与多模型路由由应用自己的代码控制。

因此核心关系是：

```text
自然语言请求
    ↓
作品状态 + 作者近期上下文
    ↓
风险与任务计划
    ↓
按需读取小说证据 / 独立检查 / 多方案搜索
    ↓
章节设计
    ↓
正文生成
    ↓
连续性 + 阅读感 + 确定性检查
    ↓
返工 / 终审
    ↓
原子提交正文与故事状态
    ↓
长期记忆与阶段摘要
```

这不是固定的一条“大模型流水线”。任务会根据当前章节风险、长期线索、阶段位置、中间检查结果和作者运行中补充要求改变执行深度。

## 2. 核心模块

### `orchestrator.py`

负责产品级任务生命周期：

- 识别讨论 / 规划 / 正文 / 重写 / 体检；
- 写章与历史章节重写；
- 长线规划和作品体检；
- 多模态资料进入创作；
- 运行中作者补充要求；
- 最终状态回写；
- 未完成创作恢复；
- 成功后的检查点压缩。

### `agent_kernel.py`

负责动态任务执行：

- 章节风险分级；
- 按风险选择独立检查方向；
- 专业任务自己调用只读作品工具；
- 合并证据与风险；
- 中间结果产生明显张力时追加挑战性检查；
- 跨 provider 会审和任务级故障回退；
- 每个任务节点持久化依赖、状态、耗时、输入摘要与输出；
- 成功结果可在同一 run 内复用，避免重复执行。

### `algorithms.py`

确定性小说控制层：

- 当前全书阶段；
- 伏笔债务/兑现优先级；
- 章节结构硬门；
- 近期结构相似度与新鲜度；
- 正文机械重复与段落诊断；
- 返工问题优先级。

模型可以建议“好不好”，但这些代码门不会因为模型返回了一个漂亮的 `pass=true` 就失效。

### `runtime.py` / `tools.py`

模型工具循环的边界：

- 工具 schema 校验；
- 只读小说工具注册；
- 每步工具调用上限；
- 整轮调用上限；
- 工具上下文字符预算；
- 重复查询复用；
- 各 provider 要求的工具消息配对保持完整。

当前小说工具包括历史章节、人物状态、事实、伏笔、阶段摘要、旧剧情搜索和作品健康度等。

### `memory.py`

长篇上下文组装：

- 当前有效事实；
- 指定章节时点的人物状态；
- 指定章节时点的伏笔状态；
- 最近正文；
- 10/50/100/500/1000 章摘要；
- 中文历史检索；
- 作者工作对话；
- 历史重写的“当时信息”与“后文兼容约束”隔离。

### `db.py`

SQLite 持久层目前负责：

- 项目/偏好；
- 对话；
- 章节/旧稿/大纲/报告；
- 事实有效区间；
- 人物时间状态；
- 伏笔当前态与事件历史；
- 阶段摘要；
- 中文全文索引与双字索引；
- 任务 run、事件、节点、检查点；
- 运行中作者补充要求；
- 作品级写作租约；
- 素材。

关键正文提交使用 `BEGIN IMMEDIATE` 事务，把章节与人物/事实/伏笔/摘要/剧情指纹一起提交。

## 3. 写下一章的决策算法

### 3.1 风险分级

风险不是让模型自报，而由后端根据作品状态计算。主要信号：

- 当前处于第几章、是否跨 10/50/100/500/1000 章阶段节点；
- 当前开放伏笔数量、即将到期和长期沉睡线索；
- 最近章节剧情指纹的重复程度；
- 请求是否包含身份揭露、死亡、决战、突破、真相、重大关系改变等高不可逆信号；
- 是否处于全书后段收束；
- 是否融合图片/资料；
- 作者选择的创作深度。

风险决定：独立检查数量、工具调查预算、章节设计候选数量、思考强度以及是否需要额外终审。

### 3.2 动态独立检查

最低安全集合始终覆盖：

- 连续性
- 人物主动性
- 连载兑现

高风险时按需增加：

- 新鲜度
- 长线结构
- 世界规则
- 读者预期

每个方向都有本轮特定关注点，并能调用小说工具读取自己的证据；不是把同一份 prompt 换几个角色名重复一遍。

### 3.3 中间观察后重规划

第一轮独立结果回来后，代码计算：

- 风险判断跨度；
- 平均置信度；
- 高风险警告密度；
- 显式分歧；
- 关键证据是否冲突。

出现高张力时，运行中新增挑战性检查，然后再形成最终共识。因此初始任务图并不是执行开始前就完全固定。

### 3.4 章节设计搜索

根据风险搜索 1–3 份独立设计。候选重点分别偏向：

- 冲突压力；
- 人物主动选择；
- 兑现与信息差。

`ChapterDesignGuard` 检查：

- 本章功能是否明确；
- 开场是否存在不稳定因素；
- 人物有没有明确目标与阻力；
- 转折是否真的改变局面；
- 主角有没有主动选择；
- 选择是否有代价；
- 是否兑现了前面积累的承诺；
- 是否一章同时乱开过多新坑；
- 场景前后状态是否改变；
- 章尾是否改变下一章的行动条件。

结构不合格先重新设计，而不是先花长正文成本再补救。

## 4. 写后检查与返工

正文生成后并行进行：

- 设定/时间线/人物知识边界检查；
- 连载读者追读感检查。

随后综合质量检查。

代码另外强制：

- 硬冲突非空 => 不通过；
- 总分按维度重新计算，不信模型自报 total；
- 明显过短 => 不通过；
- 机械重复、段落形态异常等进入返工项；
- 质量卡线、意见冲突或高风险章确认度不足 => 额外终审。

返工使用问题分类和优先级，不把所有意见混成一句“请润色”。

## 5. 历史章节重写

重写第 46 章时先构建第 46 章时点的作品状态：

- 第46章及以前的事实/人物知识是可用历史；
- 第47章以后只作为后文兼容约束；
- 后面发生的事情不能被人物在第46章“提前知道”。

重写前分别检查当时连续性、后文兼容、人物弧和伏笔影响。通过后：

- 原稿进入 `chapter_version`；
- 当前章节正文替换；
- 受影响的事实有效区间重算；
- 人物状态重放；
- 伏笔事件时间线重放；
- 覆盖该章的阶段摘要失效并重建；
- 当前最新章号保持不变。

## 6. 长篇记忆

### 6.1 事实是时间状态，不是平面 Key-Value

`subject + predicate` 发生变化时，旧事实设置 `valid_to_chapter`，新事实从当前章生效。

这避免几千章后同时把：

```text
钥匙 = 冰冷
钥匙 = 发烫
```

都当成“当前真相”。

### 6.2 中文历史召回

SQLite 常见 unicode61 对中文分词不适合长篇检索。墨境同时维护：

- FTS trigram 候选；
- 中文双字索引；
- 主键回取正文，避免两个 FTS 虚拟表直接 JOIN 造成多千章退化；
- 最终按真正共享的查询片段重新排序。

### 6.3 Rolling Horizon

不在第一天生成“3000章详细大纲”。

- 全书层锁终局和不可逆大节点；
- 卷层锁方向；
- 未来 50–100 章用阶段簇；
- 最近 10–20 章细化；
- 真正写当前 1–3 章时才形成精确章节设计。

这避免早期低质量规划绑死后面两千章。

## 7. 运行中作者补充要求

每个长任务拥有 `run_id`。可安全接入的正文、重写、规划和体检任务允许作者在运行中追加要求。

要求写入 `run_author_notes`，在明确的阶段边界消费：

- 章节设计前；
- 正文开始前；
- 每轮审校/返工前；
- 长线规划/体检的综合阶段；
- 历史重写的写稿/审稿阶段。

如果补充出现在审稿阶段，当前稿被强制视为需要下一版吸收，避免“页面说收到但实际上直接提交”。

## 8. 持久运行与恢复

运行状态、节点和检查点保存到数据库。

恢复分两级：

1. **中间阶段**：使用同一个 run id 继续，写作租约允许同一个逻辑任务续租；不同任务仍互斥。
2. **准备提交阶段**：如果正文、故事状态和元信息都已经准备好，只差事务落盘，恢复直接提交，不再调用模型重新生成。

成功提交后，状态成为单向终态。后续浏览器断线或最后一个进度事件发送失败不会把它改回 failed/cancelled。

成功任务删除重复的大型中间检查点，只保留最终 durable 状态和轻量节点轨迹；失败任务保留现场用于诊断与恢复。

## 9. 多模型路由

`ModelRouter` 支持：

- provider capability 过滤；
- planner / creative / editor / vision 分工；
- 需要 tools/vision/json 时选择支持能力的 provider；
- 单任务 provider 失败时回退其他可用 provider；
- 关键章节可把独立检查尽量分散给不同 provider；
- 未配置 provider 自动排除。

模型层与小说状态层解耦，因此更换模型不会重写作品数据结构。

## 10. 安全与资源边界

当前主要边界：

- 单次上传大小限制；
- 图片真实解码和像素上限；
- PDF/JSON/UTF-8 真实校验；
- 附件必须属于当前作品；
- 工具 schema + 调用预算；
- 作品级写作租约；
- SQLite busy timeout + `BEGIN IMMEDIATE`；
- 客户错误信息与上游技术错误分离；
- 页面输出使用 HTML escaping；
- 流式响应断开不反压持久后台任务。

## 11. 当前部署边界

现在是单机/私有部署架构。公开多租户 SaaS 仍应增加 PostgreSQL、对象存储、账户/租户、密钥托管、额度/计费、分布式任务队列、备份和可观测性。
