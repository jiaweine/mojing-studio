# 墨境 · 长篇创作室

<p align="center">
  <strong>把聊天变成持续创作，把一本书写成一个长期存在的作品世界。</strong>
</p>

<p align="center">
  对话式长篇小说创作平台 · 3000 章级长期记忆 · 多模型 · 多模态 · 可恢复创作
</p>

![墨境长篇创作室](docs/images/product-preview.png)

墨境不是“输入一段提示词，生成一章文字”的聊天壳。它把一部连载小说当作持续演化的作品：章节、人物状态、世界事实、伏笔、阶段目标、作者刚刚谈好的写作要求和参考素材都会被分别保存，并在下一次创作时按需要取回。

作者面对的仍然只是一个自然的聊天窗口。你可以直接说：

> 继续下一章，但先别揭钥匙来历，让林夜主动选择去北塔。  
> 重写第 46 章，保留后面第 80 章已经成立的关系。  
> 规划接下来 100 章，最近 20 章细一点。  
> 查一下周岚第一次知道“2:17”是什么时候。  
> 这章正在写，补一句：林夜不能主动杀人。

后台会自己决定需要读取哪些旧章节、人物、线索与设定，先把本章职责和冲突设计清楚，再写正文、检查连续性和阅读质量；需要返工时会带着具体问题重写。已经保存的结果不会因为浏览器断线而倒退成失败，未完成的创作也可以继续完成。

## 产品体验

### 一个作品，一个长期对话

左侧是作品，中间是持续对话，右侧是章节、人物、线索、设定、素材和创作记录。作者不用学习后台结构，也不需要在十几个管理页面之间跳转。

- **继续写**：承接最近剧情与长期约束，生成完整下一章。
- **重写旧章**：指定任意历史章节，兼顾当时信息边界和已经写出的后文。
- **规划长线**：远处只锁方向，近期细化到可执行冲突和兑现。
- **作品体检**：找设定冲突、人物失忆、伏笔欠账、节奏疲劳与重复桥段。
- **讨论故事**：像和长期合作的主编一样聊天，近期明确要求会延续到后续创作。
- **运行中补充要求**：正文、重写、长线规划和体检进行时，可以继续补一句要求；系统会在下一个安全阶段吸收，而不是让作者等任务完全结束。
- **参考图与资料**：人物、场景、地图、封面参考、PDF、Markdown、TXT、CSV、JSON 都可以进入作品。

### 客户界面只讲创作

后台可以很复杂，但页面不向作者展示执行图、调度器、内部检查角色或模型协议。客户只会看到“正在核对旧剧情”“正在检查人物状态”“正在整理线索”“章节已经保存”这类有意义的状态。

![创作引擎设置](docs/images/engine-settings.png)

移动端采用专注写作模式；作品资料通过顶部“资料”进入，不把桌面三栏硬塞进窄屏。

## 为什么它适合 3000 章长篇

长篇真正困难的不是上下文窗口不够大，而是**哪些信息现在仍然有效、人物此刻知道什么、哪些线索已经兑现、旧规则什么时候被新规则取代，以及当前章节到底需要想起哪一段过去**。

墨境因此不把前面几百万字反复塞给模型，而是把作品拆成不同时间尺度：

- 最近章节原文保留现场感；
- 事实带有生效区间，状态改变时旧值退役而不是与新值同时“有效”；
- 人物按章节保存位置、目标、认知、关系、资源、伤势等状态；
- 伏笔和连载承诺有提出、推进、兑现与预计回收位置；
- 每章有剧情指纹，用于发现连续重复的结构；
- 10 / 50 / 100 / 500 / 1000 章形成不同尺度的阶段摘要；
- 历史正文有中文友好的检索索引；
- 重写旧章时，未来章节只作为“不能改坏后文”的约束，不会混进人物当时的知识。

当前代码重新构造 3000 章合成作品后，自然中文长句仍能在毫秒级召回第 137 章只出现过一次的旧线索；详见 [验证记录](docs/VALIDATION.md)。

## 一次“继续下一章”真正发生什么

下面是技术实现的概念顺序，作者页面不会显示这些内部名称。

1. 读取当前作品阶段、最近章节、仍有效事实、人物状态、伏笔债务与相关历史。
2. 根据章节位置、长期线索、近期重复、作者要求和重大剧情信号计算本章风险。
3. 选择本章真正需要的独立检查方向，并让它们按权限读取作品证据。
4. 中高风险章节搜索多份章节设计，而不是拿第一份提纲直接写。
5. 先用代码检查“目标—阻力—选择—代价—兑现—章尾变化”是否成立，不合格先修结构。
6. 生成完整正文。
7. 并行检查事实连续性与连载阅读感，再进行质量评审。
8. 硬冲突、明显过短、机械重复等问题由代码兜底，模型自己的“通过”不能覆盖这些错误。
9. 未过线时根据问题类型重写，而不是只做表面润色。
10. 通过后以一个事务保存正文、人物、事实、线索、摘要和剧情指纹；要么全部成功，要么全部不落库。
11. 成功后压缩不再需要的中间大草稿，只保留最终状态和轻量执行记录。

详细实现见 [技术架构](docs/ARCHITECTURE.md)。

## 自研执行内核

模型只是可更换的能力来源，不是整个产品的控制器。墨境自己的代码负责：

- 当前任务该做多深；
- 要读哪些作品资料；
- 一轮最多允许多少工具调用与上下文；
- 是否需要额外检查或重新规划；
- 多个章节设计如何做确定性择优；
- 什么情况绝对不能提交；
- 写作中作者的新要求什么时候接入；
- 浏览器断线后后台任务是否继续；
- 服务中断后从哪里继续；
- 如何防止两个标签页或两个进程同时写出同一个章号；
- 哪些中间结果可以复用，哪些必须重新执行。

这使它属于“**对话是控制入口、后台持续执行真实任务**”这一类产品，而不是单轮文本生成器。它的深度不在通用文件系统或终端操作，而在小说世界状态、长篇连续性、连载结构与写后回写。

## 多模型与多模态

可以同时连接多家模型服务，按作品分别指定剧情规划、正文、校对和参考图理解。当前适配层支持：

- DeepSeek
- OpenAI
- Anthropic Claude
- Google Gemini
- OpenAI-compatible 私有网关

不指定时会使用项目默认服务；当前任务需要图片能力而所选模型不支持时，会选择已配置的视觉模型。关键章节还可以开启“关键章节双重检查”，让独立检查尽量使用不同已连接服务，降低同一模型重复同一盲点的概率。

模型名全部由 `.env` 覆盖，因此项目不会把业务逻辑绑定死在某个厂商版本。

## 快速启动

推荐 Python 3.11+。

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env
```

至少配置一家模型服务。例如：

```env
NOVEL_STUDIO_DEFAULT_PROVIDER=deepseek
DEEPSEEK_API_KEY=your_key_here
DEEPSEEK_MODEL=deepseek-v4-pro
```

启动：

```bash
python run.py
```

打开：

```text
http://localhost:8000
```

### 多家模型同时配置

`.env.example` 已经列出 DeepSeek、OpenAI、Anthropic、Gemini 和自定义兼容接口。页面里的“创作引擎”可以按作品选择：

- 剧情规划
- 正文主笔
- 校对与体检
- 参考图理解
- 章节质量线
- 最多整章重写次数
- 创作深度
- 关键章节双重检查

## 多模态资料

支持：

```text
PNG / JPG / WebP / GIF
PDF
TXT / Markdown / CSV / JSON
```

上传阶段会做真实格式校验：坏图、超大像素图、伪 PDF、损坏 JSON 和非 UTF-8 文本会在进入创作前直接拒绝，避免写到一半才失败。

图片会先形成可复用的视觉笔记，再进入人物、场景与正文；文本/PDF 会在字符预算内进入相关任务上下文。

## 工程结构

```text
app/
  main.py          HTTP API、流式对话、素材上传与恢复入口
  orchestrator.py  小说任务执行、正文/重写/规划/体检闭环
  agent_kernel.py  风险驱动任务规划、独立检查、动态重规划与执行记录
  algorithms.py    章节结构门、新鲜度、正文诊断与返工优先级
  runtime.py       受控工具循环、预算、缓存与工具协议
  tools.py         小说专用只读工具
  memory.py        长篇上下文组装、历史/当前状态隔离与阶段压缩
  db.py            作品、章节、事实、人物、线索、运行、检查点与索引
  providers.py     多模型统一适配、能力过滤、路由与故障回退
  prompts.py       小说垂直的角色规范与结构化输出契约
  static/          客户端页面、样式、交互和本地视觉素材

tests/
  test_agent_kernel.py
  test_product.py

docs/
  ARCHITECTURE.md
  PRODUCT_SPEC.md
  VALIDATION.md
  images/
```

## 当前部署边界

这份工程定位是**可直接运行的单机 / 私有部署创作产品**。它不是已经补齐账号、组织权限、支付、额度、对象存储、分布式队列和运营后台的公开多租户 SaaS。

如果要面向大量外部客户运营，建议继续增加：

- PostgreSQL 与对象存储；
- Redis / durable queue；
- 账号、团队与租户隔离；
- API Key 托管与日志脱敏；
- 套餐、额度、计费与支付；
- 备份、监控、告警和审计；
- 分布式任务租约与 worker 编排。

这些基础设施不改变小说创作内核本身。
